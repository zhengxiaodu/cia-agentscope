Section · 01

技术演进：
LLM → Agent → Harness

模型越来越聪明，但「聪明的模型」不等于「能干活的系统」。

第一部分回答一个问题：为什么行业从单模型，走到 Agent，又走到 Harness。这是理解我们项目设计的前提。

Limit · 单模型的边界

单个 LLM：聪明的大脑，无力的手脚

🧊

知识是冻结的

训练数据有截止日期。今日新闻、实时行情、公司内部制度——模型一概不知道，也查不到。

🤐

只会说，不会做

输出只能是文本。不能联网搜索、不能查知识库、不能渲染图表、更不能执行有副作用的操作。

🌀

没有状态与规划

上下文窗口有限，长链条任务容易跑偏、遗忘中间结论；没有权限边界，企业场景无法直接上。

复杂任务需要的不止「会思考」，还要「能行动、有记忆、守规矩」。

Part 01 · 技术演进单个 LLM 的能力边界
企业里的真实任务：查实时数据、查内部制度、画图、让用户确认再执行——单模型一个都做不了。于是有了 Agent。

Evolution · Agent 时代

Agent：给模型装上工具，但工程设施各自为政

Agent = LLM + 工具 + ReAct 循环

模型在「思考 → 调用工具 → 观察结果 → 再思考」的循环里完成任务，能力大幅扩展。

  • — 接搜索：解决实时信息
  • — 接知识库：解决私域知识
  • — 接渲染工具：把答案变成图表、卡片
  • — 我们的问答平台，核心也是一组 Agent

但复杂任务下，痛点浮现

  • — 模型接入、会话管理、沙箱、持久化、UI……每个项目重复造轮子
  • — 能力与运行时耦合：换模型、加工具都要动代码
  • — 缺统一权限、隔离与可观测性，企业级落地难
  • — 单 Agent 单循环，难以支撑多意图、多智能体协作
Part 01 · 技术演进Agent 的进步与不足
Agent 解决了「会用工具」，但把这些能力组装成一个可靠系统的工程层——谁来管会话、管沙箱、管权限、管渲染？——仍然各写各的。这一层就叫 Harness。

The Answer · 运行时层

Model + Harness = Agent

模型负责「思考」，Harness 负责「执行」——把模型之上的工程设施标准化。

模型接入·可替换
工具调度·技能化
会话状态·可恢复
沙箱隔离·安全执行
权限管控·企业级
组件渲染·富交互
可观测·全链路
一句话给 Harness 下定义：模型之上、应用之下的那层运行时。接下来介绍的我们这个项目，本质上就是在企业场景里自建了一层 Harness。

Section · 02

项目架构：
配置中心 · 后端 · 前端

能力放在配置里，执行放在运行时里，体验放在终端里。

项目是一个企业级智能问答平台：多智能体、可配置、带交互卡片。整体分三块：管理侧的配置中心、FastAPI 后端运行时、前端对话终端。

Architecture · 系统总览

三层架构：能力配置 → 编排执行 → 交互呈现

Part 02 · 项目架构总体架构
从下往上看：配置中心定义「有哪些能力、谁能用」；后端负责「怎么组合与执行」；前端负责「怎么呈现与交互」。虚线下发、运行时消费。

Config · 配置中心

配置中心：一切能力皆可配置

配置之外还有一层用户权限：登录时与管理端融合，决定每个用户能见哪些智能体、哪些技能。

Part 02 · 项目架构配置中心
关键理念：能力不是写死在代码里的，是登记在配置里的。新增一个「制度问答智能体」？加一段 YAML 即可，下一页的创新点会展开。

Runtime · 后端

后端：编排引擎 + 沙箱工作区

🧭 编排链路

  • — 登录时融合本地配置与管理端权限，缓存 Redis
  • — 每轮对话：改写 → 意图识别 → 路由到智能体
  • — 单意图直接执行；多意图按关系并行 / 流水线 / ReAct
  • — 意图识别与工作区装配并行进行，压低首字延迟

📦 沙箱与工具

  • — OpenSandbox：按用户分配沙箱，按会话隔离目录
  • — 技能文件在首次对话时注入沙箱，随取随用
  • — 工具工厂闭包注入会话/用户上下文（搜索、知识库、卡片、反馈）
  • — 每个智能体只拿到自己技能子集对应的工具箱
Part 02 · 项目架构后端
后端就是我们的「迷你 Harness」：模型之上，把编排、隔离、工具、状态管理全部收口。技术栈 FastAPI + AgentScope + OpenSandbox。

Terminal · 前端

前端：流式对话 + 组件化卡片

  • ① 流式体验

    回答逐字流出，工具调用过程实时可见——用户等得住，因为看得见它在干活。

  • ② 组件化渲染

    后端产出统一组件协议：折线图、指标卡、自定义卡片（cardType + schema）。前端按配置中心的模板渲染，新增卡片类型前端零改动。

  • ③ 闭环交互

    确认卡片上用户点一下 → 回传 feedback → 唤醒挂起中的智能体，同一轮对话继续往下走。

Part 02 · 项目架构前端
前端的重点不是页面，是协议：文本流 + 组件流 + 反馈通道，三件事撑起「能看、能点、能续」的对话体验。

Section · 03

创新点
与实现思路

三个创新点，一条主链路。

三个创新点按「静态 → 动态 → 隔离」展开，最后用一次对话的完整链路把它们串起来。

Innovation · 01

配置驱动的多智能体编排

📉 传统做法

  • 新增智能体 = 写代码、改路由、重新发版
  • 工具对所有智能体全局暴露，职责不清
  • 提示词散落在代码里，运营无法触碰
→

📈 本项目

  • YAML 声明式注册：新增智能体零代码、免发版
  • 每个智能体只见自己绑定的技能子集，天然隔离
  • 意图 / 提示词 / 技能全部配置化，管理端可运营

上线「制度问答」「深度调研」等新智能体，从排期开发变成改配置 + 发卡片。

Part 03 · 创新点配置驱动编排
举例：上个月新增 feedback_confirm 技能并绑定到通用问答智能体，只加了两个文件和两行 YAML。注册表机制在运行时按技能名筛选装配工具箱。

Innovation · 02

卡片反馈：同轮暂停-恢复

对比传统「文字追问 → 下一轮再答」：体验从两轮对话压缩为一轮。

Part 03 · 创新点卡片反馈同轮恢复
这是项目里最有「运行时」味道的设计：工具执行中途可以挂起等待人类输入，恢复后仍在同一个 ReAct 循环里。人机协同的最小闭环。

Innovation · 03

沙箱隔离的技能工作区

👤

按用户分配沙箱

用户之间完全隔离；沙箱可复用，TTL 淘汰 + 崩溃自动重建，高可用有兜底。

📁

按会话隔离目录

同一用户的多会话互不干扰；文件产出、上传解析各归各的目录。

🧬

技能按需注入

技能文件在首次对话时写入沙箱；智能体只能在自己工作区内读写，越界即拒绝。

安全模型很朴素：模型生成的任何内容都先当不可信代码对待，跑在隔离边界内。

Part 03 · 创新点沙箱技能工作区
技能注入是懒加载的：登录只做配置融合，第一次问答才真正建沙箱、注入技能文件。沙箱存活期内技能不变，TTL 过期后下次对话自动刷新到最新版。

Walkthrough · 实现思路

一次对话的完整链路

Part 03 · 实现思路一次对话的完整链路
串起来讲：配置决定能力边界，意图决定谁来干活，沙箱决定在哪干活，ReAct 决定怎么干活，组件协议决定怎么呈现。五个环节里 2 和 3 是并行的。

Section · 04

新一代 Harness：
DeepSeek Harness

「一切皆插件」的开源 Agent 运行时（2026.08 · MIT）。

最后把视野拉出去：我们自建的这层 Harness，业界已经出现了标准化的开源实现。看看 DeepSeek Harness 交出的答卷。

Landscape · 定位

DeepSeek Harness：模型之上的开源运行时

它是什么

  • — 不是又一个大模型，是 Model + Harness = Agent 的官方实践
  • — 底座 Cordis：一个只管「插件加载 / 卸载 / 依赖管理」的元框架
  • — 源自 Koishi 作者，经跨平台、海量插件生产验证后整体并入
  • — 全链路可追溯：模型看到的每个 token 都有记录

「一切皆插件」

  • — 模型、工具、技能、会话、沙箱、存储、循环、调度、连 UI 都是插件
  • — 配置即架构：改配置即热替换，不改源码、无需重启
  • — 四种运行模式：标准 / PTC 编程式工具调用 / 极简 / 创意
Part 04 · DeepSeek Harness定位与主张
和我们自建的思路同源，但更彻底：我们配置化的是「能力」，它把「运行时本身」也插件化了。PTC 模式值得一提——让模型写代码来编排多轮工具调用，降低长链路往返成本。

Mechanisms · 核心机制

撑起「一切皆插件」的三大机制

♻️

可逆副作用

任何注册动作都必须登记撤销函数，卸载时 LIFO 逆序清理。失败原子性、级联清理、运行时热插拔由此成立。

🔌

服务与事件

能力消费走服务、状态广播走事件，双通道松耦合；作用域链天然隔离——子层可见父层，反之不可见。

📦

预设与作用域

全局—预设—会话的作用域链；一份插件树多会话复用，工具可见性按作用域运行时遮蔽，不再全局二元。

设计哲学一句话：把「卸载」和「加载」放到同等地位，热插拔才不是口号。

Part 04 · DeepSeek Harness核心机制
重点讲可逆副作用：传统 DI 容器只管绑定不管解绑，插件一多就幽灵回调、连接泄漏。Cordis 把清理变成框架的结构性保证。安全上 Code Mode 用 worker_threads 而非 vm 沙箱，隔离边界内不信任任何模型输入——和我们沙箱思路一致。

Takeaway · 启示

对照 Harness：我们做对了什么，接下来做什么

✅ 已经做对的

  • 配置驱动：意图 / 智能体 / 技能全部声明式
  • 能力分装：技能 = 文档 + 工具，卡片 = 模板 + schema
  • 隔离与安全：沙箱工作区、权限白名单、单槽反馈对账
→

🧭 可以借鉴的

  • 插件化运行时：工具 / 技能从「配置注册」走向「热插拔」
  • 可逆性设计：注册即登记撤销，组件可回滚可替换
  • 统一模型服务接口：面向接口编程，模型随装随换

Agent 的竞争，正在从「模型效果」延伸到「运行时质量」。

Part 04 · 启示对我们的启示
收束观点：我们项目在企业场景里自建了一层实用主义 Harness，方向和 DeepSeek Harness 互相印证。后续演进可以考虑向插件化、可逆性靠拢。
