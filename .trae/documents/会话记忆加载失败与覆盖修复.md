# 会话记忆加载失败与覆盖修复 实施计划

## 摘要

修复 `orchestrator_service.py` 中两个关联 bug：
1. `_load_agent_state` 在 `_trim_state_context` 后的 `state_dict` 仍有内容（context 有记忆），但函数返回 None
2. 每次对话覆盖 `agent_states` 表里原来的 state，导致历史记忆永久丢失

Bug 2 是 Bug 1 的连锁反应：加载返回 None → 创建空状态 agent → 保存空 state 整体覆盖原数据。**修复 Bug 1 后 Bug 2 自然解决**，无需对保存路径加额外保护。

## 当前状态分析

### Bug 1 根因（[orchestrator_service.py:525-547](file:///workspace/app/services/orchestrator_service.py#L525-L547)）

```python
async def _load_agent_state(...):
    if not (session_service and session_id):
        return None
    try:
        state_dict = await session_service.load_agent_state(session_id, agent_id)
        if state_dict:
            state_dict = self._trim_state_context(state_dict)  # ← 用户观察到此处 state_dict 有内容
            return AgentState.model_validate(state_dict)        # ← 此处抛异常
    except Exception:
        logger.debug(...)  # ← 静默吞掉，debug 级别默认不输出
    return None
```

`AgentState.model_validate(state_dict)` 抛异常被 `except Exception` 捕获，`logger.debug` 级别太低默认不可见，最终 `return None`。

可能的异常来源（通过代码审查推断，无需运行时确认即可覆盖）：
- `AgentState.context: list[Msg]`，`Msg` 有 `@model_validator(mode="after")` 校验 user/system 消息的 content blocks（[agentscope/message/_base.py:116-126](file:///root/.pyenv/versions/3.14.7/lib/python3.14/site-packages/agentscope/message/_base.py#L116-L126)）。历史数据中若 user 消息混入非 text/data block，触发 `_assert_user_content_blocks` 的 ValueError
- `ToolCallBlock.suggested_rules: list[PermissionRule]`、`permission_context` 等嵌套字段在版本演进中类型变化，旧数据反序列化失败
- `reply_context.structured_schema` 等 `Type[BaseModel] | dict | None` 字段在旧数据中的格式不兼容

### Bug 2 根因（覆盖链路）

1. `_load_agent_state` 返回 None（Bug 1）
2. [registry.py:141-145](file:///workspace/app/agents/registry.py#L141-L145) `create_agent` 收到 `agent_state=None`，创建空 `AgentState`
3. agent 执行时 `context` 只有本轮新对话
4. [orchestrator_service.py:650-653](file:///workspace/app/services/orchestrator_service.py#L650-L653) 和 [orchestrator_service.py:861-865](file:///workspace/app/services/orchestrator_service.py#L861-L865) `final_state = agent.state.model_dump()` 只含本轮 context
5. [mysql_session_dao.py:122-130](file:///workspace/app/dao/mysql_session_dao.py#L122-L130) `save_agent_state` 是 UPSERT（`ON DUPLICATE KEY UPDATE state = VALUES(state)`），整体覆盖
6. 数据库原有完整 context 被空/极短 context 覆盖 → **历史记忆永久丢失**

## 提议改动

### 改动 1：`_load_agent_state` 分层容错反序列化 + 日志升级

**文件**：[app/services/orchestrator_service.py](file:///workspace/app/services/orchestrator_service.py)

**改什么**：重写 `_load_agent_state` 方法（line 525-547），分层容错：

1. **第 1 层（完整加载）**：`AgentState.model_validate(state_dict)` 成功则直接返回
2. **第 2 层（仅恢复 context）**：第 1 层失败时，从 `state_dict` 提取 `context` 字段，逐条 `Msg.model_validate(m)`，跳过无法解析的消息，用 `AgentState(context=[...])` 重建（其余字段用默认值，后续保存时会重新填充）
3. **第 3 层（兜底）**：第 2 层也失败或 context 为空时返回 None

**日志升级**：
- 第 1 层失败：`logger.warning("完整加载 agent %s 状态失败，降级到仅恢复 context", agent_id, exc_info=True)`
- 第 2 层跳过某条消息：`logger.warning("跳过无法解析的消息（index=%d）", idx, exc_info=True)`
- 第 2 层最终 context 为空：`logger.warning("agent %s 状态 context 全部解析失败，将新建", agent_id)`

**为什么**：用户观察到的现象明确指向 `model_validate` 抛异常被静默吞掉。分层容错确保即使部分字段不兼容，也尽量保留最核心的多轮对话记忆（context），避免一次反序列化失败导致整段历史丢失。

**怎么改**（伪代码）：

```python
async def _load_agent_state(
    self,
    session_service: Any,
    session_id: Optional[str],
    agent_id: str,
) -> Optional[AgentState]:
    if not (session_service and session_id):
        return None
    try:
        state_dict = await session_service.load_agent_state(session_id, agent_id)
    except Exception:
        logger.warning(
            "[OrchestratorService] 读取 %s 状态失败，将新建", agent_id,
            exc_info=True,
        )
        return None
    if not state_dict:
        return None

    # 截断 context 为最近 N 条（仅内存截断，不落库）
    state_dict = self._trim_state_context(state_dict)

    # 第 1 层：完整加载
    try:
        return AgentState.model_validate(state_dict)
    except Exception:
        logger.warning(
            "[OrchestratorService] 完整加载 agent %s 状态失败，降级到仅恢复 context",
            agent_id, exc_info=True,
        )

    # 第 2 层：仅恢复 context（跳过无法解析的消息）
    from agentscope.message import Msg
    raw_context = state_dict.get("context") or []
    if not isinstance(raw_context, list):
        return None
    recovered: list = []
    for idx, m in enumerate(raw_context):
        if not isinstance(m, dict):
            continue
        try:
            recovered.append(Msg.model_validate(m))
        except Exception:
            logger.warning(
                "[OrchestratorService] 跳过 agent %s 的第 %d 条消息（解析失败）",
                agent_id, idx, exc_info=True,
            )
    if not recovered:
        logger.warning(
            "[OrchestratorService] agent %s 状态 context 全部解析失败，将新建",
            agent_id,
        )
        return None
    logger.info(
        "[OrchestratorService] agent %s 状态降级恢复：context %d/%d 条",
        agent_id, len(recovered), len(raw_context),
    )
    return AgentState(context=recovered)
```

**注意**：`Msg` 导入放在方法内（局部导入），避免在模块顶部引入对 agentscope.message 的强依赖（与现有代码风格一致，`_run_single_agent_path` 也是方法内局部导入）。

### 改动 2：Bug 2 自然解决说明（无需代码改动）

**文件**：无代码改动，仅说明。

**为什么**：Bug 2 的根因是 Bug 1 导致加载返回 None → 创建空 agent → 保存空 state 覆盖原数据。改动 1 修复后：
- 加载不再返回 None（除非数据库里根本没有该 agent 的 state，此时新建是正确行为）
- agent 会带着历史 context 执行
- 保存时 `final_state` 包含旧 context + 本轮新 context
- UPSERT 覆盖行为变成正确的"更新"（新 state 包含完整历史）

**不加额外保护的理由**：在保存路径加"对比 context 长度避免空覆盖"的检查会引入过度工程：
- 正常流程中首轮对话 context 本来就短（只有 1 轮），会被误判为"空覆盖"
- 判断"何时该跳过保存"的阈值难以确定
- Bug 1 修复后加载不会失败，保险层没有实际触发场景

## 假设与决策

1. **假设**：`AgentState.model_validate` 失败的根因是历史数据与当前模型 schema 部分不兼容（具体哪个字段不重要，因为分层容错对所有字段失败都生效）。若根因是数据库连接/SQL 错误，第 1 层 try 已覆盖（读取 state_dict 阶段失败会直接返回 None，不会进入反序列化）。

2. **决策**：不在保存路径加"空覆盖保护"。理由见改动 2。

3. **决策**：`_trim_state_context` 保持在第 1 层之前执行（与原代码一致），这样第 2 层恢复 context 时已经是截断后的最近 N 条，避免恢复全部历史再截断的浪费。

4. **决策**：第 2 层恢复时只重建 `context` 字段，其余字段（`permission_context`、`tool_context`、`tasks_context` 等）用 `AgentState` 默认值。理由：这些字段都是会话内可重建的（permission 默认 BYPASS 由 registry 创建时覆盖，tool_context 是文件缓存可重新填充，tasks_context 是任务上下文本轮重建），多轮记忆的核心是 `context`。

5. **决策**：不修改 DAO 层（`save_agent_state` 的 UPSERT SQL 保持原样）。覆盖行为本身正确，问题在加载侧。
