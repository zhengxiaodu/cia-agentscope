# 安全敏感服务改造与上传免改写 实施计划

## 概要

四项改动：
1. 适配 `/sensitive/check` 新返回格式（顶层 `reason`/`hitSources`，废弃嵌套 `semantic` 对象）
2. 用户输入改为纯词典检测（新接口 `/sensitive/dict-check`），输出审核仍走 `/sensitive/check`
3. 新增 `.env` 开关 `SENSITIVE_ENABLED`（默认开），关闭时输入输出均不审核
4. 会话存在未绑定消息的上传文件时，跳过问题改写（rewriter）

## 现状分析（Phase 1 探索结论）

- [sensitive_service.py](file:///workspace/app/services/sensitive_service.py)：`check_sensitive(text, stage)` 统一入口，POST `SENSITIVE_SERVICE_URL`，请求体 `{"text", "threshold"}`；`_blocked_from_response()` 从**嵌套** `semantic.{reason,category,source}` 解析；兜底结构含 `category` 字段；Langfuse span 输出含 `category`。
- [routes/chat.py](file:///workspace/app/routes/chat.py#L53-L61)：用户输入审核调用 `check_sensitive(user_input, stage="input")`，命中发 `message_replace` 事件并终止流。
- [chat_service.py](file:///workspace/app/services/chat_service.py#L575-L581)：输出审核调用 `check_sensitive(final_output, stage="output")`（**保持不变**）。
- [orchestrator_service.py](file:///workspace/app/services/orchestrator_service.py#L920-L932)：多意图路径步骤③调用 `rewriter.rewrite(user_input, history)`；单 agent 短路路径（L905-918）本就不做改写。
- [upload_file_dao.py](file:///workspace/app/dao/upload_file_dao.py)：已有 `load_unbound_parsed`/`bind_message_id`；上传文件以 `message_id IS NULL` 标识"未被消费"。
- [config.py](file:///workspace/app/config.py#L134-L140)：`SENSITIVE_SERVICE_URL/THRESHOLD/TIMEOUT`；[.env](file:///workspace/.env#L87-L93) 中 URL 为完整路径 `http://25.59.38.152:30017/sensitive/check`。

### 3. [app/services/sensitive_service.py](file:///workspace/app/services/sensitive_service.py)（核心）

**a) 内部结果结构变更**（`_FALLBACK_RESULT` / `_blocked_from_response`）：
- 删除 `category` 字段；`source`（str）改为 `hit_sources`（list）
- 新格式：`{"blocked", "reason", "hit_sources": [], "sensitive_words": [], "raw"}`

**b) `check_sensitive(text, stage)`**（输出审核用，函数名/签名不变）：
- 新增 `SENSITIVE_ENABLED` 开关检查（关闭时 `_fallback("client-skip")`）
- 请求体不变：`{"text", "threshold"}`
- 解析新格式：`blocked = hasSensitiveWord`、`reason = data.reason`（顶层）、`hit_sources = data.hitSources`、`sensitive_words = data.sensitiveWords`

**c) 新增 `dict_check_sensitive(text, stage="input")`**（输入词典审核）：
- 同样受 `SENSITIVE_ENABLED` 与空文本短路控制
- URL 由 `SENSITIVE_SERVICE_URL` 调用时派生（末段 `/sensitive/check` 替换为 `/sensitive/dict-check`；不匹配后缀则记 warning 并兜底放行）——调用时派生而非模块级常量，保证测试 monkeypatch `SENSITIVE_SERVICE_URL` 生效
- 请求体仅 `{"text": text}`（按用户约定，不带 threshold）
- 响应 `{code, hasSensitiveWord, sensitiveWords}`；命中时构造 `reason = "命中敏感词：词1、词2"`、`hit_sources = ["dictionary"]`
- 复用 Langfuse 埋点（span 名 `sensitive-dict-check`）与异常兜底逻辑

**d) HTTP 层重构**：`_do_check(text)` 拆为通用 `_post_sensitive(url, payload) -> dict|fallback`（HTTP 调用 + code/hasSensitiveWord 校验），两个入口各自做结果字段解析。

**e) Langfuse span 输出**：`category`/`source` 字段替换为 `hit_sources`。

**f) `build_message_replace_event` 不变**（仅用 `reason`，新旧结构兼容）。

## 假设与决策

1. **"有上传文件"判定** = `upload_files` 中存在 `message_id IS NULL` 记录（不论解析状态/类型）——字面语义；解析中或不可解析的文件同样跳过改写。文件在首轮问答结束后即绑定，影响范围有限。
2. **dict-check URL 派生**：不新增环境变量，由现有 `SENSITIVE_SERVICE_URL` 后缀替换得到（当前 .env 以 `/sensitive/check` 结尾，派生成功）。
3. **开关粒度**：`SENSITIVE_ENABLED` 同时控制输入与输出审核（用户要求"关闭时不对输入输出做任何安全审核"）；原有 `SENSITIVE_SERVICE_URL` 留空仍等效关闭。
4. **dict-check 命中时的 reason**：服务不返回 reason，客户端构造 `"命中敏感词：xxx"`，保证前端 `message_replace` 提示有具体原因。
5. 输入审核改 dict-check 后，**输入阶段不再做语义检测**（性能取舍，用户明确要求）；语义检测仅在输出阶段生效。
